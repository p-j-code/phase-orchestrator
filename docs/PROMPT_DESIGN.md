# Prompt Design Notes

The two system prompts (`prompts/guide-system.md`, `prompts/dev-system.md`) are the most important files in this repo. Output quality depends on them.

## Guide agent — role and constraints

The guide is responsible for: planning, prompt generation, reviews, handoffs. **It never writes production code.** This separation is enforced via directory permissions in `.claude/settings.json` (guide-cwd is `&lt;project&gt;/`, not `&lt;project&gt;/workspace/`).

Three reasons for separating guide from dev:

1. **Context isolation**: Guide carries plan + project history. Dev starts fresh each phase. Without isolation, dev context bloats across phases and quality degrades.
2. **Specialization**: Guide prompt biases for "think globally about architecture and sequencing." Dev prompt biases for "execute one well-defined task end to end."
3. **Cost/budget**: Guide can use Opus when needed (planning, reviews — infrequent calls). Dev uses Sonnet by default (frequent calls).

## Dev agent — role and constraints

Dev gets a phase prompt + workspace state + nothing else. It writes code, commits, writes a completion report, exits.

Critical: dev MUST commit before exiting, with the exact message format. The orchestrator uses git history to know which phase produced which code. If a dev session fails to commit, the orchestrator can't reliably resume.

## Phase prompt structure

A good phase prompt (generated by guide) includes:

- **Goal**: 1-2 sentences. What does this phase accomplish?
- **Acceptance criteria**: Testable bullets. "Endpoint X returns Y for input Z."
- **Files**: Expected files to create or modify.
- **Constraints**: Tech stack, conventions, what NOT to do.
- **Testing**: How to verify before committing.
- **Commit instruction**: Exact commit message format.
- **Context the dev doesn't already have**: Anything not visible in workspace files.

## When the guide should suggest model overrides

Default Sonnet handles most phases. Override to Opus when:

- Architectural design phase (early structural decisions)
- Heavy algorithmic work (performance optimization, complex parsers)
- Debugging across many files
- Refactor that affects API surface

The guide should set `model_override: "claude-opus-4-7"` and `max_turns_override` (higher) in `plan.json` for these.

## Handoff document quality

A bad handoff doc forces the next guide to re-read everything. A good one lets it pick up immediately. Optimize for:

- **Concrete state, not narrative**: "Phase 4 added feature X to file Y" not "We worked on the auth flow."
- **Decisions with rationale**: "Chose Library A over B because B has no TypeScript support."
- **Pitfalls already hit**: Spare the next guide from re-discovering them.

## Reviews

The 3-phase review is the orchestrator's quality control loop. Without it, dev drift accumulates silently.

A good review checks:

- Did each phase meet acceptance criteria? (Read phase reports.)
- Are conventions holding? (Read workspace.)
- Is the remaining plan still right? (Read plan.json.)
- Should anything be replanned?

Reviews on Opus catch more issues than reviews on Sonnet. The cost difference is worth it.
